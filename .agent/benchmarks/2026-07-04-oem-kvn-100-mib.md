# OEM KVN 100 MiB parsing baseline

## Purpose

Measure the first CCSDS OEM KVN implementation's bounded-memory event path and
the cost/benefit of ordered Rayon state collection. These results are a local
baseline, not a cross-machine performance guarantee.

## Environment

- Date: 2026-07-04
- OS: Microsoft Windows NT 10.0.26200.0, x86_64-pc-windows-msvc
- CPU identifier: AMD64 Family 23 Model 113 Stepping 0, AuthenticAMD
- Logical processors: 16
- Rust: rustc 1.96.1 (31fca3adb 2026-06-26), LLVM 22.1.2
- Build profile: Cargo `bench` optimized profile
- Criterion: 0.8.2, `--quick`

## Workload

`crates/ccsds/benches/oem.rs` deterministically generates just over 100 MiB of
valid single-segment OEM KVN with repeated seven-field state records. The
streaming case consumes events without retaining states. Sequential and Rayon
collection both return the complete typed `Oem` document and preserve source
order.

Command:

```powershell
cargo bench -p orskit-ccsds --bench oem -- --quick
```

## Results

| Path | Criterion time interval | Point throughput |
| --- | ---: | ---: |
| Blocking streaming events | 2.3263-2.3889 s | 42.757 MiB/s |
| Ordered Rayon collection | 994.32 ms-1.0195 s | 100.07 MiB/s |
| Sequential collection | 2.5454-2.7765 s | 38.586 MiB/s |

On this workload and host, Rayon collection was approximately 2.59 times the
throughput of sequential collection. Streaming remains the memory-bounded API;
the parallel path assumes the full input is already resident and additionally
allocates the returned state document plus line/event indexes.
